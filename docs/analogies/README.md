# Analogies

Analogies that have earned their place — built during a real session, tested against the record,
and found to carry weight rather than decorate. They exist so that later sessions **reach for one
of these rather than invent a fresh one**, and so that an explanation given today uses the same
image as an explanation given six months ago.

## What these are for

Two jobs, and the second is the less obvious one:

1. **Explaining.** When something on this project has to be understood before it can be ruled on.
2. **Reasoning.** A good analogy is a working model — it makes some consequences obvious that the
   formalism buries, and an agent may legitimately use one to *find* a question worth asking. The
   [think tank](./think-tank.md) produced two findings that way before either was measured.

## The rules

- **An analogy is never evidence.** It generates hypotheses; it never settles one. Where an
  analogy and a reading disagree, the reading wins and the analogy gets amended — see the
  *Where it has been wrong* section each entry carries.
- **Extend, don't fork.** If an existing analogy nearly fits, extend it and record the extension.
  A second competing image for the same object costs more than it buys.
- **Record who built it.** These are shared vocabulary, and a session that does not know an image
  is the user's own may talk them out of their own intuition.
- **Keep the project's own words.** `CONTEXT.md` is the glossary and it is shared ground: an
  analogy translates *into* the project's vocabulary rather than replacing it. What an analogy
  defers is the *field's* vocabulary — the words that arrive with a paper.
- **Nothing here overrides `CONTEXT.md`, the spec or an ADR.**
